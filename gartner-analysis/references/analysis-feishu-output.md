# Markdown 与飞书文档输出协议

## 默认顺序

先生成并验证 Markdown；只有用户明确要求“输出为飞书文档”“发布到飞书”或同义表达时，才执行飞书文档转换。飞书文档是 Markdown 的发布副本，不替代本地 Markdown 源文件。

## 飞书格式优化门槛

在任何飞书创建或更新之前，必须调用/遵循 `feishu-doc-optimizer`：检查标题从 H1 开始且层级严格递进、编号体例统一、正文与表格组件选择合理、表格对齐与列宽可读、高亮块克制、引用格式一致。该 Skill 不负责读写；实际 fetch、create、block 更新和回读验证仍使用 `lark-doc`。

## 新建文档

使用 `lark-doc-convert`，并遵循 `lark-doc` 的创建工作流：先检查认证，再预处理 Markdown，使用 `docs +create` 创建到用户“我的文档”库（`--parent-position my_library`），最后读取并验证文档内容和 URL。重复创建同主题文档时使用版本号。

## 更新文档

用户指定已有飞书文档时，先按 `lark-doc` 规则 fetch 最新 block ID；只做 `block_replace`、`block_insert_after`、`block_delete` 或必要的 `str_replace`，禁止 `overwrite` 全文覆盖。每轮写入后重新 fetch 验证。

## Gartner 年度对比输出

年度对比文档中，每个技术的量化指标、定义与叙事、驱动因素、障碍、用户建议五类对比后，必须紧邻放置一个分析师小结，年度总结另行提炼。小结应说明变化或持平、其意义、Gartner 判断和采用/采购含义，并保留页码或表内证据标识；“见上表”“仅供参考”和纯证据边界不能作为小结。定义、驱动、障碍和建议中有两个及以上独立点时，使用真实 `<ul><li>`；有顺序关系才用 `<ol><li>`，连续论证用段落。

### 全文并列信息的分段

全文所有并列信息容器，包括普通段落、表格单元格、callout、卡片、对照栏和引用块，若同时包含两个及以上独立信息点，尤其是以 `[Gartner 原文]`、`[Gartner 估算]`、`<推理>`、`<估算>` 或其他证据标签标记的内容，必须拆成真实 `<ul><li>`。每个列表项只承载一个事实、估算或判断，页码和来源标签放在对应列表项末尾。

当各信息点之间存在连续因果论证，保留为段落；只有并列信息才拆列表。不要把多个证据点用分号串成一段，也不要在内容容器中用行首短横线模拟列表。表格继续用于承载“技术 × 属性”或“厂商 × 评价维度”等结构化字段；列表化只调整容器内部结构。原有“标签 + 说明”的内容可按以下方式转换：

```xml
<td><ul>
  <li>[Gartner 原文] SASE 平台为 Check Point SASE；需在 Infinity Portal 内集成两套管理控制台（PDF 6）。</li>
  <li>[Gartner 估算] 约 1,000 家企业客户；运营以北美、欧洲和亚太为主。</li>
  <li>[Gartner 原文] 未来投资聚焦 AI 安全、SASE 平台统一与自主 DEM（PDF 6）。</li>
</ul></td>
```

判断阈值：出现两个及以上独立标签、独立页码证据、独立事实、独立限制或独立行动建议时，使用无序列表；出现 `①②③`、`一是/二是/三是`、`第一/第二/第三` 等显式并列标记时，无论所在容器为何，均视为强制列表化。只有一个完整判断或不可拆分的连续论证时，使用段落。写入飞书后必须回读确认对应并列信息容器中保存为真实列表块（`<ul><li>`），而非纯文本分号串。

## 内容与报告边界

- 保留 Markdown 已验证的标题、表格、引用和证据边界；飞书导入前处理连续 blockquote、加粗属性行、Mermaid 和美元符号等兼容问题。
- 飞书发布失败时保留 Markdown，明确报告失败原因，不把“创建 API 返回成功”当作内容验证成功。
- 新建或更新完成后交付飞书 URL；无法取得或验证 URL 时只交付 Markdown，并说明状态。
