## 1 共同规则

先完成同类型两份翻译，再建立结构化底表。HC 只与 HC 比较，MQ 只与 MQ 比较。不要从第 7 份交叉洞察倒推变化结论。

双年分析固定使用：

1. 总结概述；
2. Gartner 年度核心结论；
3. 年度变化总览；
4. 完整变化底表；
5. 关键变化详细分析；
6. 方法限制；
7. 参考文献。

第 4 章必须覆盖全部对象；第 5 章按 P0→P3 展开，不能只选择容易说明的个案。

### 1.1 分析深度要求

变化底表和变化总览只是分析的基础，不是分析的替代。每一项列入底表的变化都必须在正文中有对应的分析段落或证据块，回答以下问题：

- **为什么变化**：Gartner 在正文中给出了哪些驱动因素或障碍因素来解释这一变化？
- **背景是什么**：这一变化发生在什么市场、技术或厂商层面的背景下？两年间发生了什么外部事件推动了这一变化？
- **影响是什么**：这一变化对技术成熟度判断、厂商竞争定位或市场评估框架产生了什么影响？是否改变了评估标准的口径？

不允许出现"只列变化名称和方向、不解释原因和影响"的底表行。如果某项变化缺少足够的 Gartner 原文支撑来回答上述问题，在底表中标注"Gartner 未在正文中详细解释"并在证据块中说明证据不足。

### 1.2 新增和移除技术/厂商的分析要求

新增技术或厂商时，必须引用 Gartner 在正文中给出的新增理由和背景说明，不能只列出名称。移除技术或厂商时，必须引用 Gartner 在 Off the Hype Cycle 或 Vendors Added and Dropped 部分给出的移除原因。Gartner 对移除通常给出明确的退场分类（成熟退场、被其他技术吸收、重命名、范围调整或停止追踪），必须引用原始分类而非自行推断。

如果多项移除技术呈现出共同模式（如均被更广泛的架构概念吸收），可以在分析中用 `<推理>` 标记综合推导这一模式，但每项移除的原始原因仍需逐一引用。


## 2 HC 分析

### 2.1 结构化字段

对每项 Innovation Profile 记录：

- Technology；
- Hype Cycle Stage；
- Benefit Rating；
- Years to Mainstream Adoption；
- Market Penetration；
- Definition；
- Why Important；
- Business Impact；
- Drivers；
- Obstacles；
- User Recommendations；
- Sample Vendors；
- Gartner 原文页码。

### 2.2 年度匹配

按以下顺序匹配技术：

1. 规范化后精确名称；
2. 标准编号、括号和大小写归一化；
3. Definition 与报告明确说明的重命名；
4. 仍不确定时列为“可能重命名”，不要强制合并。

### 2.3 变化分类

- 阶段上升、下降或不变；
- Benefit Rating 升级或降级；
- 主流采用年限加速或延迟；
- 新增、移除或重命名；
- Definition、Drivers、Obstacles、Recommendations 或 Sample Vendors 实质变化。

“从 HC 移除”不自动等于成熟。分别核对 Gartner 是否说明成熟退场、被其他技术吸收、重命名、范围调整或停止追踪。


### 2.4 HC 分析的 HC/PM 分离与逐技术深挖

双年 HC 分析应将 Hype Cycle 和 Priority Matrix 分开分析，各自输出关键变化总结和详细展开。第 3 章（年度变化总览）应分别呈现 HC 层面和 PM 层面的变化概览。

第 4 章（完整变化底表）应包含技术全景矩阵表，列为：技术名称、Hype Cycle 阶段、Priority Matrix（Benefit + Years）、Market Penetration、趋势判断、决策关注优先级。最后一列按筛选条件「{期望膨胀期, 稳步爬升复苏期, 生产成熟期} ∩ {主流采用年限为 2 年内或 2–5 年} ∩ {收益为中等（Moderate）或高（High）}」标记优先关注技术（★/☆）。若任务带有领域配置，再按该配置解释优先级；通用协议不预设企业规模或行业。

第 5 章（关键变化详细分析）应分为两个子节：5.1 Hype Cycle 关键变化详细展开和 5.2 Priority Matrix 关键变化详细展开，各自包含证据块。

在文档末尾增加附录 A：各技术深挖。逐项技术输出：
- 总结概述段（基于阶段和 Benefit Rating 判断技术当前状态）
- 企业用户启示段（基于 Benefit Rating 给出适用性判断，不得出现"厂商应如何做"的语句，只描述技术对用户的意义、适用边界和风险）
- 技术属性表（行：Hype Cycle 阶段、Priority Matrix 两维度、Market Penetration、Maturity、Gartner 原文页码；Definition、Why Important、Business Impact、Drivers、Obstacles、User Recommendations、Sample Vendors 等字段应以 H3 子标题形式在属性表后展开，不得省略）

## 3 MQ 分析

### 3.1 结构化字段

记录：

- 市场名称、定义与范围；
- Mandatory 与 Optional Capabilities；
- 纳入、排除和 Honorable Mention 条件；
- Ability to Execute 与 Completeness of Vision 评价标准；
- Strategic Planning Assumptions；
- Vendor、Quadrant、Summary、Strengths、Cautions；
- 厂商实体、并购和品牌归属；
- Gartner 原文页码。

### 3.2 年度匹配

先判断参评实体是否一致。并购、拆分或品牌合并后，旧厂商与新实体不能只按名称机械比较；在变化底表中写明实体关系和可比性。

### 3.3 变化分类

- 象限移动；
- 新增、移除或降为 Honorable Mention；
- 市场定义、Mandatory Capabilities 或评价权重变化；
- Strategic Planning Assumptions 变化；
- Strengths 与 Cautions 的新增、消失、强化或弱化；
- 并购后参评实体改变。

MQ 图上的相对位置变化只有在 PDF 提供可可靠提取的坐标或明确文字时才描述。不要凭视觉估计细小位移或虚构数值坐标。

### 3.4 变化深度要求

象限移动不得只标注从 X 到 Y。必须分析：

- Gartner 在两年间对该厂商的 Strengths 和 Cautions 表述发生了什么变化：逐项对比 Strengths 和 Cautions 的新增、消失、强化或弱化，引用原文中的具体表述。
- 评估标准变化是否影响了该厂商的定位：如果市场定义或评估标准权重在两年间发生了变化，分析这些变化对该厂商评分的可能影响。
- 厂商自身行动是否推动了变化：厂商在两年间的产品发布、收购、平台整合等行动是否被 Gartner 在 Strengths 或 Cautions 中引用。

市场定义变化必须分析其评估框架影响。评估标准权重变化必须分析对不同类型厂商的差异化影响。战略规划假设变化必须分析定义升级的含义。


## 4 关键变化证据块

P0/P1 使用机器可审计边界：

```markdown
<!-- change-priority: P1 -->
### 5.1 变化标题

- 变化事实：只陈述两份 Gartner 报告可直接确认的变化。
- Gartner 证据：「[G001](#ref-g001)」「[G002](#ref-g002)」
- Gartner 结论：说明 Gartner 如何解释该变化。
- 外部证据：「[S001](#ref-s001)」「[V001](#ref-v001)」
- 支持程度：一致 / 部分一致 / 冲突 / 证据不足
- 限制：说明口径、时间、样本或来源限制。
<!-- /change -->
```

P0/P1 至少包含一个 G 类引用和两个不同外部引用，其中至少一个为 S、P 或 R。P2 至少一个 G 和一个外部来源。P3 可以只引用 Gartner，但不得扩展成行业结论。

如果全量底表复核后不存在 P0/P1，在第 5 章写 `<!-- no-p0-p1: 具体判定理由 -->`，并详细展开最重要的 P2/P3。不要为满足模板而把普通变化抬高等级。

外部材料只用于验证 Gartner 判断。不要让厂商公告覆盖 Gartner 原文，不要把厂商营销语言直接写成分析结论。


### 4.0 变化分析开头：总结性描述

每个关键变化的证据块必须以 1-2 段总结性描述开头，不重复底表数据，而是提炼"这个变化意味着什么"。总结应遵循以下原则：

- 不重复变化事实本身（如"X 从 A 阶段移动到 B 阶段"），而是解释这个变化的含义和重要性
- 指出该变化的本质驱动因素：是技术成熟、市场热度变化、评估标准转变，还是三者兼有
- 将该变化置于更大的叙事框架中：它代表了什么趋势、对什么假设构成了挑战或确认
- 如果变化在 Hype Cycle 模型中呈现反常特征（如阶段与采用年限不一致），在总结中点明并解释

示例风格（不要机械模仿措辞，但应追求同等的洞察密度）：“Agentic NetOps 在一年内从技术萌芽期进入期望膨胀期，说明 Gartner 已将其视为企业网络运营的新中心议题。这个变化不是因为技术已经成熟，而是因为企业和厂商都在把自主运维视作下一阶段效率突破口。”总结段落可以引用 Gartner 原文中的关键措辞作为叙事锚点，但不需要在总结段落中给出完整引用——具体引文仍在后续证据块中逐一标注。

如果某条 P2 或 P3 变化缺少足够信息来撰写有洞察力的总结，在底表中标注"Gartner 未在正文中详细解释"并在总结中诚实说明。


### 4.1 Gartner 结论字段的要求

Gartner 结论字段不得只复述变化事实。必须包含 Gartner 在正文中对该变化的具体解释，包括 Gartner 列出的 Drivers 或 Obstacles 中与该变化直接相关的条目，以及 Gartner 在 Strengths 或 Cautions 中对该厂商能力变化的具体措辞。引用时应保留 Gartner 的关键措辞（如 Integration progress delivered 或 AI operational scope），使读者可以回到原文核对。

### 4.2 限制字段的要求

限制字段不得只写实际部署可能滞后等泛泛之语。必须具体说明该变化是否与评估标准变化相关，以及该变化在多大程度上是 Gartner 评价框架转变而非厂商或技术本身的实质性变化。


## 5 单年提炼

固定六节：

1. 总结概述；
2. Gartner 单年核心结论；
3. 完整结构化底表；
4. 重点内容详细提炼；
5. 方法限制；
6. 参考文献。

单年 HC 底表覆盖全部 Innovation Profile；单年 MQ 底表覆盖市场、方法和全部 Vendor Profile。不要出现“上升”“下降”“新增”“移除”“跃升”或跨年箭头。

## 6 禁止混写

HC/MQ 分析只陈述 Gartner 原文明确包含的 Business Impact、User Recommendations、市场定义和厂商评价，不自行推演行业影响、企业用户影响或行动含义。不要出现：

- 厂商应该投入什么；
- 指定厂商能力差距或竞争策略；
- 产品路线图、研发优先级或市场行动建议；
- HC×MQ 的跨报告趋势判断。

这些内容统一进入交叉洞察文档。
