# 两份 HC 到飞书技术线索报告

## 触发、范围与完成定义

用户要求“给两份 HC，产出完整飞书技术线索文档”“按终稿样例输出”或同义目标时，使用 `presentation_format=hc-feishu-insight`、`report_type=HC`、`feishu_output=true`。由 `gartner-analysis` 连续编排 `extract → annual-hc → presentation → 飞书发布 → 回读验收`。用户无需逐阶段重新发令，也无需提供机器参数。

这是最终交付配置，不增加第二个 HC 分析入口。只有两份 PDF 时，直接完成必要提炼和分析；不要求用户先提供底表、完整中文翻译或 MQ。只有明确要求全文翻译或完整研究套件时，才额外交付相应译稿。本配置取代最终呈现中的七章分析骨架和通用 HC 八项模板；原来的证据、字段和可比性规则仍适用。

“与样例一样”指相同的阅读结构、字段完整度、图表组合和飞书原生组件，不指复制样例技术、年份、公司布局或编辑痕迹。若给出样例链接，先只读 fetch 当前结构及必要画板预览；样例不能自动成为写入目标。两份同系列报告只输出该系列，不补入其他领域，不生成空的多领域分组。

完成必须同时有：已核对数据、最终报告本地源稿、HTML／SVG、飞书 URL、最新 full fetch 和通过的交付检查。API 创建成功、Markdown 检查通过或 HTML 能打开均不能单独代表完成。资源、原生编号或引用未通过时，交付状态为部分完成并列明缺项。

## 1. 输入与证据交接

唯一必需的内容输入是两份可读取、年份递增且系列与范围可比的 HC PDF。年份和标题从 PDF 提取。企业／产品背景、已布局证据和筛选范围是可选输入；缺失时先完成报告，用通用采用视角，不阻塞在反复询问偏好。

复用 `hc-comparison-data.json` 保存数据真值，避免另建互相漂移的字段底表：

- `reports`：每份 PDF 的路径、SHA-256、标题、Gartner ID、年份、发布日期、页数、HC 图页、Priority Matrix 图页和技术原名全集。
- `profiles`：每个技术、每个年份分别记录原名、Hype Cycle Stage、Maturity、Benefit Rating、Years to Mainstream Adoption、Market Penetration、Definition、Why Important、Business Impact、Drivers、Obstacles、User Recommendations、Sample Vendors；每个字段保留值、报告 ID、物理页码和缺失状态。原文没有的字段写明未提供，不能以空字符串代表已提炼。
- `mapping`：稳定技术 ID、两年原名、持续／新增／移出／改名／拆分／合并／不可比、连续性证据、继承与新增范围。仅字符串接近不足以认定同一技术；拆分或合并保留多对多关系，不强行压成一对一。
- `changes`：五项指标各年值与变化、Definition／Drivers／Obstacles／Recommendations 的实质变化、原因证据、分析师判断与限制。
- `chart`：归一化点位、定位依据、阶段边界与编辑器锚点，按 [HC 编辑器契约](hc-comparison-editor.md) 生成。

必须区分曲线位置 `Hype Cycle Stage` 与采用成熟度 `Maturity`；二者不能共用一个值。百分比区间从 5%–20% 变为 20%–50% 只能说区间上移，不能据此计算精确倍数。采用年限是预测窗口，不能不加说明地转为确定商用年份。

两年技术全集取并集形成总览，最新一年全部技术默认进入详情。仅移出技术可只保留总览和退场原因；若用户限定相关性范围，可减少详情，但每个省略项须留在覆盖清单并记录理由。新增不填虚构前年值，移出不自动解释为成熟、失败或淘汰。

## 2. 分析先于排版

先按 `gartner-hype-cycle-analysis` 完成全部变化和技术判断，再交给呈现层。呈现阶段发现结论缺口，应回到分析补证，不能在排版时新编结论。

每个技术的洞察至少回答：今年与去年怎样变化，Gartner 怎样解释，采用含义是什么，证据限制在哪里。优先解释组合信号，例如曲线进入低谷同时渗透率上升；没有指标变化时比较叙事和约束，不制造变化。年度总结由这些逐技术判断向上归纳，不从预设“三条主线”反推事实。

证据边界：

- Gartner 原文、分析师判断、外部核验与企业内部状态分开标记。HC 单独支持的采用、架构或采购含义可以在年度分析中明确标作分析师判断；这不构成 HC×MQ 交叉洞察，也不要求添加 MQ。
- “已布局”必须有用户提供的产品现状或获确认路线图证据。两份 HC 或 `Sample Vendors` 不能证明用户企业已布局。无依据时写“企业布局状态未提供”，仍给出有证据的技术采用判断。
- “需考虑布局”“保持关注”属于分析建议，说明适用场景和条件；没有企业背景时不写成该企业已作出的决策。指定厂商竞争对标和 HC×MQ 趋势仍由原专项入口处理。
- 默认仅根据两份报告形成报告内比较。来源不足不臆造外部事件；用户要求外部核验、或结论依赖当前标准／市场状态时再检索一手来源。未完成外证的结论标为报告内判断／待核验；若使用 P0/P1 证据等级，仍须满足共享外证门槛，不能把“业务优先关注”等同于证据等级。

## 3. 最终文档树与组件

文档标题是独立 `<title>`。参考样式的正文主章节用 `h1`，每个正文 heading 使用飞书原生自动编号，文字不带序号。通用格式 Skill 的“单个 H1 作为文档标题”不能覆盖用户明确指定的这种 `<title> + 多个正文 h1` 样式；从 h1 逐级递进即可。

单对 HC 默认结构如下；代码块中缩进代表层级，不是手工编号：

```text
文档标题：{系列}技术线索洞察分析｜{Y1}–{Y2}
来源说明：两份报告、时间、范围、验证状态
h1 洞察总结
  全篇洞察 callout
  重点技术方向画板
  技术布局与采用窗口总结表
  布局状态定义与依据说明
h1 技术线索分析
  h2 线索总结
    榜单变化、HC 与 Priority Matrix 各自主线、组合判断
  h2 技术线索分析
    h3 年度对比总览
      可调整双曲线对应的飞书画板
      双年 HC／Priority Matrix 原图对照
      全技术年度变化表
    h3 {Technology English}
      技术洞察 callout
      技术／主题／内容详情表
    ...按覆盖清单继续各技术
h1 方法与限制
h1 参考文献
```

仅当实际输入跨多个领域时，在“技术线索分析”下增加领域 h2，每个领域内部的上述层级下移一级。报告分组也仅在真实需要时增加。不要复制样例里的“不相关（去掉）”、人员 @、删除线或残留跳级编号。

### 洞察总结

最高层 callout 提炼少量完整判断，每条对应正文中的技术证据。随后用一张画板表达“主线 → 技术组合 → 解决的问题 → 验证指标”；主线和卡片数量由证据决定。指标若不是报告原文，标为建议验证指标，不编造目标数值。无企业布局资料时，画板也不能含“我司已布局”结论。

总结表的四个逻辑列固定为：

| 分类 | 技术布局结论 | 未来规模应用窗口期 | 未来重点技术趋势 |
|---|---|---|---|

分类取报告范围或有依据的技术主题；第二列区分企业状态与建议，第三列按当前 Benefit 与采用时间窗口汇总，第四列按当前曲线阶段／实质主题变化组织。列表数量与技术详情、图表和数据底表一致。不照搬固定的交集筛选公式冒充 Gartner 优先级，也不遗漏 Transformational 等原始收益档位。

### 年度总览与原图

双曲线画板来自 [可调整 HTML 流程](hc-comparison-editor.md)。默认先完成自动排版和浏览器验收并发布当前已核对版本，同时交付 HTML 供用户继续调整；除非用户要求先手调确认，否则不在“等待用户调整”处停住整篇交付。以后有新布局时，仅更新这张明确授权的画板。

两年各保留 HC 与 Priority Matrix 两种原图，共四张，标注年份、图名、来源页码。可放等宽双栏：一栏一个年份，各自先 HC 后 Priority Matrix；窄页可顺序排布。原图从本次 PDF 提取，不能拿样例文档图片或自动生成的 alt 描述当作原始数据。

年度表覆盖两年技术并集，四列为：

| 技术 | {Y2} 年变化（相比于 {Y1} 年） | 关键变化 | 变化解读 |
|---|---|---|---|

第二列逐项列 Stage、Years、Benefit、Market Penetration、Maturity 的双年值；第三列说明叙事／指标的实质变化与原因；第四列给有证据的采用含义和限制。新增、移出、不可比明确标记，不能用单个上升箭头替代。

### 逐技术详情

每项按“技术英文标题 → 洞察 callout → 三列表”排列。洞察包含关注结论、年度组合变化和采用含义；公司相关性和布局状态只有有依据才写。

三列表遵循 [技术详情表契约](presentation-contract.md#hc-固定输出)：第一列只有技术原名并纵向合并所有主题行；第二列是主题；第三列是内容。必需主题为“技术、技术成熟度、优先级矩阵、市场渗透率、定义、为什么重要、业务影响、驱动力、障碍、用户建议、供应商”；存在 Maturity 时另加“成熟度（Maturity）”主题，或在指标总览明确保留，不能混为 Stage。

详情以最新年完整 Profile 为主，必要字段写前年值或变化，不能只剩差分而丢失当前定义和建议。多项独立 Drivers／Obstacles／Recommendations 使用原生列表；忠实整理 Gartner 用户建议与分析师建议分开。供应商统一标为“示例厂商”，不能写“主导者以及挑战者供应商”。

## 4. 飞书发布流程

1. 本地 Markdown 保存已核对的阅读内容；数据 JSON 保存字段与来源。XML 是飞书发布候选，负责合并、列宽、callout、分栏、图像和画板。不得把普通 Markdown 转换成功当作复杂版式完成。
2. 按 `lark-doc` 创建工作流选择内容契约，执行 `init-draft`，使用返回的草稿路径编写 XML，执行 `parse` 并检查 `data.assessment.status`。原生表格直接使用 `rowspan`、`colgroup`、真实 `<ul><li>`；不用转换后手工猜合并位置。
3. 新建到“我的文档”，使用 `--parent-position my_library`；用户已指定已有可写文档则最新 fetch 后局部更新，不能全文 overwrite。只有只读样例链接时，新建独立文档，不把样例作为发布目标。授权创建在执行时由用户“输出飞书文档”目标提供；单纯审阅 Skill 不执行创建。
4. 采用模板语义一致的淡色 callout 和少量紫色关键判断。表头居中、所有单元格垂直居中；详情列宽约按 11%／19%／70% 分配，合计匹配真实页宽，不固定照抄样例的像素。用 XML 保留颜色，不能依赖 Markdown 保留 `span`。
5. 两张画板分别承担方向总结和年度双曲线；具体插入／更新语法使用当前 `lark-doc` 和 `lark-whiteboard`。先写可用内容，再局部修复资源失败；不得因为局部失败再创建第二篇同主题文档。
6. 标题原生编号写入后检查最新 outline／full fetch 的 `seq-marker`。只有 `seq="auto"` 不能作为成功证据；缺失时使用当前可用的编号修复流程，再次 fetch。无法完成就标明编号未验收，不写入手工前缀掩盖。
7. 引用先建立参考条目，fetch 得到真实 block ID，再把正文 G 类引用转换为该条目的完整文档锚点；公开外证直接链接原始 URL。正文显示完整可点击 `[G001]` 等代号，XML 用 `<a href="URL">[G001]</a>`，需要代码样式时在其外层包 `<code>`。分析底稿中的旧引用引号／本地 `#ref-*` 不能原样当成已可用的飞书锚点。
8. 每轮结构写入后重新 fetch，不使用旧 ID。最终保留 `fetch-final.json`（含 reference_map）和 XML，再核对正文、两图、四张原图、技术集合、表格、编号和引用。对画板导出 raw 与 preview；检查标签、年份、线条、裁切和可编辑性降级。

本配置用单个技术 callout 汇总五类比较的分析师判断，并在详情对应字段保留必要变化说明；不机械添加五个重复小结打散样例结构。判断深度仍遵循 `analyst-summary-guide.md`。

## 5. 交付清单与可重复验收

保存 `hc-delivery-manifest.json`，把生成前的覆盖清单与发布后的真实 ID 连起来。最小字段如下（代码中的示意值由实际输入／回读替换，不上传到 Skill 仓库）：

```json
{
  "years": [2024, 2025],
  "source_reports": [
    {"year": 2024, "technologies": ["Example A"]},
    {"year": 2025, "technologies": ["Example A", "Example B"]}
  ],
  "technologies": [
    {"id": "a", "display_name": "Example A", "names": {"2024": "Example A", "2025": "Example A"}, "detail": true},
    {"id": "b", "display_name": "Example B", "names": {"2025": "Example B"}, "detail": true}
  ],
  "document_id": "actual-created-document-id",
  "blocks": {"summary_table": "st", "overview_table": "ot", "summary_board": "sb", "comparison_board": "cb"},
  "source_figures": [
    {"block_id": "i1", "year": 2024, "kind": "hype-cycle", "page": 2},
    {"block_id": "i2", "year": 2024, "kind": "priority-matrix", "page": 3},
    {"block_id": "i3", "year": 2025, "kind": "hype-cycle", "page": 2},
    {"block_id": "i4", "year": 2025, "kind": "priority-matrix", "page": 3}
  ]
}
```

`source_reports.technologies` 来自每份 PDF 的独立完整清点，不能反过来从已写正文生成以掩盖遗漏。`names` 的各年值须覆盖该全集；同年拆分／合并的多个原名可用数组表示，并在数据文件另存映射依据。`detail=false` 必须含 `exclusion_reason`。这是展示覆盖映射，不授权计算不可比实体的指标变化。额外记录数据／源稿路径、每阶段状态与缺口、图表编辑版本、视觉检查记录、引用检查和最终交付状态。

生成候选时用本地 XML 检查结构；发布后用新 fetch 检查实际落库结构：

```bash
python3 scripts/validate_hc_delivery.py --manifest /path/to/hc-delivery-manifest.json --xml /path/to/draft.xml
python3 scripts/validate_hc_delivery.py --manifest /path/to/hc-delivery-manifest.json --fetch /path/to/fetch-final.json
```

脚本检查覆盖清单、文档身份、章节、紧邻 callout、总览表与合并详情表、列宽、两张画板、双年四图、原生编号和引用结构。本地检查仅为 `LOCAL ONLY`，不能代替发布验收；此配置不用要求三份翻译／七章稿的 `validate_outputs.py --mode hc` 冒充最终交付检查。

人工必须核对：PDF 全集和页码、每项变化语义、五项指标、详情字段、Gartner 与推理边界、企业布局证据，以及图表视觉和引用实际跳转。脚本通过不代表语义已核验。输出报告源稿、HTML、调整后 SVG／布局 JSON／PNG、数据及清单、飞书链接和 QA；源 PDF、业务资料与回读只保存在用户任务目录。
