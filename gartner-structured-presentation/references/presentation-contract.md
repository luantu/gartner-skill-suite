# Gartner HC/MQ 结构化章节呈现协议

## 适用范围

输入必须是已完成 extraction 的 HC 或 MQ 结构化内容，并尽量同时提供同市场两年分析。此协议负责章节化呈现，不重新解析 PDF，不补造缺失字段。先识别 `report_type`：`MQ` 或 `HC`。

用户要求“两份 HC 直接产出完整飞书技术线索文档”时，使用 [hc-feishu-insight 交付配置](hc-feishu-insight.md)的最终文档树和组件顺序，不使用下方通用 HC 八项顺序。共用本文件的三列表字段语义、示例厂商边界和数据完整性要求。

## MQ 固定输出

### 结构与层级

参考章节嵌入既有文档时，先读取最近的父级 heading，再沿用同一套层级，不得混用 heading 深度。若父文档的主章节是 `h2`，本章标题用 `h2`、`1.1/1.2` 用 `h3`、具体变化用 `h4`；若父文档主章节是 `h4`，则对应使用 `h4/h5/h6`。本节可见标题固定为 `1.1 关键变化`，标题后立即放整个 MQ 的洞察高亮块。不得生成 `1 关键变化`，也不得生成带“关键变化洞察”字样的独立标题；具体变化从 `1.1.2` 开始并使用下一级 heading。不要擅自从 `h1` 开始制造新的文档层级。

固定顺序：

1. `1.1 关键变化` 标题；
2. 标题后立即放整个 MQ 的洞察高亮块（不再另设“关键变化洞察”标题）；
3. 双栏或等价对照块：`2025：...` 与 `2026：...`，分别写两年主线并保留 Gartner 摘要/原文链接；
4. 在“关键变化”章节内插入厂商位置变化表；
5. Top 5（最多 5 项）关键变化详解：每项从 `1.1.2` 起，用下一级标题 + 洞察高亮块 + 变化事实/机制/证据/限制；
6. 需要时补充白板、引用或厂商官方材料，但不能用装饰性图形替代证据；
7. 限制与参考文献。

### 两张厂商表（归属不同，均保留）

关键变化章节内必须输出位置变化表：

| 厂商 | 2025 年位置 | 2026 年位置 | 主要变化 |
|---|---|---|---|

`1.2 厂商分析章节` 另行输出能力分析表，字段保持不变；每个单元格至少写清“定位/策略、可验证优势、限制或适用边界”，避免只填一个短标签：

全文所有并列信息容器（包括普通段落、表格单元格、callout、卡片和引用块）若包含两个及以上独立证据点，必须拆为真实 `<ul><li>`；特别是 `[Gartner 原文]`、`[Gartner 估算]`、`<推理>`、`<估算>` 标签不得与其他独立信息用分号串联成一段。单一连续论证才保留段落，列表项末尾保留对应页码、来源和限制。

| 厂商 | 总结 | 优势 | 劣势 |
|---|---|---|---|

不得合并两张表，也不得用任一张表替代另一张表。

### Top 5 规则

从双年变化底表按“市场意义、象限/能力移动、厂商影响、证据充分度”排序，最多输出 Top 5（最多 5 项）。每项必须包含：

- `h6` 变化标题；
- 洞察高亮块；
- 2025 与 2026 的直接事实；
- Gartner 页码或原文引用；
- 变化机制、业务含义和限制。

没有两年结构化输入时，**不得生成年度关键变化、象限移动或“重返/升至/降至”判断**；只能输出“单年观察”，并明确缺少比较基线。

## HC 双曲线可调整呈现

用户要求 HC 双曲线对比、技术迁移图或可调整 HTML 时，执行[双曲线编辑器流程](hc-comparison-editor.md)。两份 PDF 先形成可核对的年度底表，再生成双曲线 SVG 和自包含编辑器 HTML；最终用调整后 SVG 写入用户指定的飞书画板。此模式不能只交付静态图片或以下章节模板。

## HC 固定输出

固定顺序：

1. `Hype Cycle` 章节标题；
2. 全篇洞察总结高亮块；
3. 关键变化及洞察；
4. 持续存在技术的阶段变化表：

| Technology (English) | 2025 Stage | 2026 Stage | 趋势 | 解读 |
|---|---|---|---|---|

5. 新增与消失的技术表：

| Technology (English) | 年度 | Stage | Benefit Rating | 说明 |
|---|---|---|---|---|

6. Priority Matrix：

| 技术 | 阶段 | Benefit | 未来规模应用窗口 | 关注优先级 | 重点趋势 |
|---|---|---|---|---|---|

7. 技术总结：

| 分类 | 主流采用年限 | 重点技术趋势 | 重点关注技术布局结论 | {期望膨胀期，稳步爬升复苏期，生产成熟期} ∩ {主流采用年限为 2 年内或 2–5 年} ∩ {收益为中等（Moderate）或高（High）} |
|---|---|---|---|---|

8. 技术线索分析：在“技术线索分析”章节下，按“技术标题 + 洞察总结高亮块 + 技术详情表”逐项输出；只选择证据充分且对决策有意义的技术。技术标题使用当前父章节的直接下一级 heading：父章节为 `h3` 时技术标题用 `h4`，若中间还有报告标题等 `h4` 分组，则技术标题用 `h5`；不得固定为 `h6`，也不得手工写入编号前缀。

洞察总结高亮块紧跟技术标题，先写相关性或关注结论，再用一至两条完整判断概括年度变化、业务含义和建议。高亮块不替代下方完整字段。

输入同时覆盖多个业务领域或多份 HC 时，在“技术线索分析”下先按领域分组。每个领域依次输出“线索总结”和“技术线索分析”；需要年度图表或全景变化表时，在具体技术之前增加“年度对比总览”。单份 HC 不为凑层级创建空的领域或报告分组。

| 技术 | 主题 | 内容 |
|---|---|---|
| **Technology (English)** | 技术 | **Technology (English)** |
|  | 技术成熟度 | `Hype Cycle Stage (中文译名)` |
|  | 优先级矩阵 | 收益：`Benefit Rating`；主流采用年限：`Years to Mainstream Adoption` |
|  | 市场渗透率 | `Market Penetration`，双年输入时注明上一年度值 |
|  | 定义 | `Definition` |
|  | 为什么重要 | `Why Important` |
|  | 业务影响 | `Business Impact` |
|  | 驱动力 | `Drivers` |
|  | 障碍 | `Obstacles` |
|  | 用户建议 | `User Recommendations` |
|  | 供应商 | 仅按原文写“示例厂商：`Sample Vendors`”或“暂无数据（源文档未提供）” |

三列的语义不得错位：第一列只放技术名称，并在飞书表格中纵向合并覆盖该技术的全部主题行；第二列只放主题名称；第三列只放该主题的内容。`Hype Cycle Stage`、`Priority Matrix`、`Market Penetration` 等属性值都属于第三列，不能写进“技术”列。Markdown 无法表达纵向合并时，后续主题行的第一列留空；发布到飞书时再合并第一列。

飞书表格的表头居中、全部单元格垂直居中。三列按“窄技术列、中等主题列、宽内容列”分配宽度，内容列占主要空间；具体像素以目标文档当前页宽为准，不复制其他文档的固定宽度。含两个及以上独立信息点的内容单元格使用真实列表。

Hype Cycle 的 `Sample Vendors` 只是示例厂商，不代表 Magic Quadrant 的领导者或挑战者。只有源报告明确给出相应分类时，才可以使用“主导者”“挑战者”等评价标签。

单年 HC 的双年表格改为“暂无年度比较数据”，不得填入推测值。

## 共同规则

- 高亮块负责洞察，不复制整张底表；表格负责完整字段。
- 定量事实、阶段、Benefit、年份、象限和厂商变化逐句保留页码引用。
- 外部证据、厂商声明和 `<推理>` 分开；厂商材料只能证明厂商动作。
- 空字段写“暂无数据（源文档未提供）”。
- Markdown 是源文件；用户明确要求飞书文档时再按 `analysis-feishu-output.md` 发布并回读。
